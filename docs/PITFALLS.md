# 踩坑记录

> 每个坑都花过真实时间。这里保留的是"判断过程"，不是答案本身。

## 1. 「构建成功」≠「改动生效」

VS 增量编译不检测 `.cu` 变化。更隐蔽的是：**语法合法的旧实现同样编译通过**，
所以"构建成功"完全没有信息量。验证改动必须**读盘核对文件内容**，
或至少确认 `.cu` 的编译时间戳/重新生成解决方案。

## 2. 行列步长常量互换（潜伏 bug）

```cpp
// 错误写法
int RowOut = (blockIdx.y * kBlockSize + ty) * kColsPerThr;  // 行用了列步长
int ColOut = (blockIdx.x * kBlockSize + tx) * kRowsPerThr;  // 列用了行步长
```

4×4 分块时 `kColsPerThr == kRowsPerThr == 4`，错误被完全掩盖；
改成 4×8 后立即爆发 —— 矩阵下半部分（行 ≥ N/2）全部为 0，
原因是行号被放大 2 倍，越界守卫提前一倍触发。

**教训**：行列用同一个常量"碰巧正确"，是最危险的代码。

## 3. 瓶颈不是 DRAM，是 LDS 指令条数

用"工作集缩小到 L2 后测速不变"证伪 DRAM 带宽假设。
真正原因：内层每轮 8 条 LDS 配 16 次 FMA（1:2），而硬件 LDS:FMA 吞吐为 1:4。
**减少字节数（如 double→float）不会改变指令条数，因此完全无效。**

## 4. 4×8 分块为什么反而更慢

`CTXIT = kColsPerThr * tx * kInnerPerT` 使同 warp 相邻线程的地址步长变为
`kColsPerThr × kInnerPerT`：

| 分块 | 步长 | `mod 32` | `gcd(·,32)` | 冲突 | 每单位计算 LDS 周期 |
|---|---|---|---|---|---|
| 4×4 | 188 | 28 | 4 | 2 路 | 0.75 |
| 4×8 | 504 | 24 | **8** | **4 路** | **1.125** |

预测 33.0 ms，实测 35.18 ms（误差 6%，由 occupancy 从 32→24 warp 解释）。

## 5. 数据集身份

曾排查"训练不收敛"数天后发现：`Train_data/Fasion/` 里那份文件格式与 MNIST 完全一致，内容其实是 **Fashion-MNIST**
（官方刻意做成 MNIST 的平替，格式与魔数完全一致）。

后来把 `data/` 换成原始 MNIST，并用画板/ASCII 渲染确认前几个样本是手写数字 5、0、4。

## 6. `Matrix_Double(int size)` 构造的是方阵

`Matrix_Double(9216)` 创建的是 9216×9216 方阵（约 679 MB），不是长度 9216 的一维数组。

## 7. 动态共享内存申请量必须与 kernel 实际使用完全一致

卷积 GPU 版里，主机按"输出尺寸"申请 shared，但 kernel 里按"输入 tile + 权重"使用：

```
需要 = (tileH*stride + K - 1) * (tileW*stride + K - 1) + ppb*K²   （float 个数）
```

两者不一致时，kernel 会越界写/读共享内存。在这块卡上表现为**设备端 illegal memory access**：
错误本身会"粘住"，在 kernel 之后第一次 `cudaMemcpy` 时才报出来，
再经 `CUDA_CHECK` 抛出未捕获异常 → 进程以 `0xC0000409`（fail-fast）退出。

**教训**：shared 大小要由同一个公式在主机和 kernel 两侧算出；"先按输出尺寸估"这种近似会出事。

## 8. 形状"瘦"的卷积不能无脑上 GPU

反传 dK 的某个调用输出只有 `1 × 8` 个块、每块 `9 × 9`，而收缩维是 `2000 × 1024`。
GPU kernel 只开得出 1 个 block、25 个线程，实测一次调用 100~227 ms，比 CPU 还慢。

**教训**：GPU 的判据不能只有"计算量大"，还要有"总线程数足够多"。
现在的调度同时检查 `macs ≥ 阈值` 和 `总线程数 ≥ 4096`。

## 9. 精度切换要配套改判据

主机 double、GPU float 之后，原来的对拍阈值（1e-9）必然失败。
浮点误差要按**相对误差**判断（本仓库卷积对拍实测 ~2e-7）。
把精度误差当成 bug 查，会浪费好几天。
