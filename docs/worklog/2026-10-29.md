## 二、矩阵乘 A 路径：锁页 + 主机侧 float 转换

### 2.1 数据流

```
主机 double
  → [AVX2 + OpenMP] ConvertDoubleToFloat
  → 锁页缓冲（只增不减、跨调用复用、首次分配后 memset 预热）
  → cudaMemcpyAsync H2D（float，字节减半）
  → GEMM kernel（输出类型模板化 TOut，直接写 float）
  → cudaMemcpyAsync D2H → 锁页
  → [AVX2 + OpenMP] ConvertFloatToDouble → out
```

- 开关：`SetMatMulTransferMode(1)`（A 路径）/ `0`（旧 pageable 路径），**运行时可切**；
- 计时：`MATMUL_GPU_TIMING=1` 打印 pack / H2D / kernel / D2H / unpack；
- 缓冲：单 stream，事件同步；`d_out` 的 double 中转在 A 路径下不再需要。

### 2.2 数值对拍（与 CPU 结果比较）

| 形状 | 相对误差 |
|---|---|
| 128×1024×2000（前向） | 1.29e-6 |
| 128×2000×1024（dW） | 1.76e-6 |
| 1024×128×2000（dA） | 4.06e-7 |
| 10×128×2000 | 3.55e-7 |
| 37×129×53（非整除怪形状） | 3.87e-7 |

FP32 累加下正常。**这是「能放心用」的证据，不是估计。**

### 2.3 单次耗时（128×1024×2000，计时开启）

| 阶段 | 数值 |
|---|---|
| pack（double→float，AVX2+OMP） | 0.8 ~ 1.1 ms |
| H2D（float） | 0.9 ~ 1.3 ms |
| kernel | 0.3 ~ 0.6 ms |
| D2H + unpack | 0.05 ~ 0.9 ms |
| **合计** | **2.2 ~ 3.0 ms** |

## 三、两个「之前不知道」的发现

### 3.1 `.cu` 主机代码的 OpenMP 一直是空转（AI 发现）

VS 的 CUDA 项目用 nvcc 编译 `.cu`，**主机编译选项和 C++ 项目的 `/openmp`、`/arch:AVX2` 是分开的**。
`imcol2_GPU.cu` 里所有 `#pragma omp parallel for` 之前**全部被忽略**——不报错，当注释处理。

**证据**：A 路径转换加上 OpenMP 前后，pack 从 **3.1 ms → 1.08 ms**。

**修复**：`高等代数.vcxproj` 的 CudaCompile 增加

```
-Xcompiler /openmp -Xcompiler /arch:AVX2
```

### 3.2 GPU 矩阵乘其实从未启用（AI 发现）

- `main.cpp` 里 `SetMatMulGpuThreshold(...)` 被注释掉了；
- `Matrix_Double_Mutiple_GPU.cu` 里默认阈值又被改成 `1024*1024*1024`。

结果：**`NN_ACCEL=gpu` 和 `NN_ACCEL=conv` 跑的是同一条路径**——之前那些「GPU 矩阵乘没收益」的 epoch 对比，其实根本没测到 GPU 矩阵乘。

修复后（阈值 2M + 形状判据），A 路径下 GPU 矩阵乘真正反超 CPU（见下）。

## 四、第一次可信的测量：Bench 工具

### 4.1 工具

- `Bench.cpp` / `Bench.h`：matmul / conv 两个微基准；
- 采样方式：**同一进程内不同模式交替跑**，机器漂移对每种模式影响相同；预热后报告 min / median / mean / GFLOP/s；
- 入口：`NN_BENCH=matmul|conv|all`；形状/模式/迭代数分别用
  `NN_BENCH_SHAPE`、`NN_BENCH_MODES`、`NN_BENCH_ITERS`、`NN_BENCH_WARMUP` 控制；
- 脚本：`run_bench.cmd`（包装 `run_bench.ps1`，绕过执行策略），结果存 `docs/bench/`。

### 4.2 矩阵乘（128×1024×2000，batch 2000 的真实前向形状）

| 模式 | min | median | 有效算力 |
|---|---|---|---|
| CPU | 6.20 ms | 6.62 ms | 84.5 GFLOP/s |
| legacy（旧 pageable 路径） | 2.07 ms | 2.40 ms | 253.9 GFLOP/s |
| **A 路径** | **1.11 ms** | 1.38 ms | **474.2 GFLOP/s** |

**A 路径 ≈ 5.6× CPU，≈ 1.9× 旧路径。**

### 4.3 形状扫描（找 GPU 启用阈值）

| 形状 | CPU | A 路径 | 结论 |
|---|---|---|---|
| 16×64×512（0.5M MAC） | 0.044 ms | 0.112 ms | CPU 胜 |
| 32×128×512（2.1M） | 0.170 | 0.148 | GPU 微胜 |
| 64×128×512（4.2M） | 0.340 | 0.141 | GPU 胜 |
| 10×128×2000（2.6M，瘦输出） | 0.324 | 0.237 | GPU 胜 |

## 五、方法论：今天真正学到的东西

### 5.1 epoch 级测量目前不可用

同一份程序、同样的参数，今天前后两次测得：

| 模式 | 上午/上次 | 本次 |
|---|---|---|
| 全 CPU epoch | 12.9 s | **22 ~ 25 s** |
| conv-gpu epoch | 9.7 s | **15 ~ 16 s** |

机器状态（后台进程 / 温度 / 功耗策略）带来的漂移 **±60%**，而 M1 想量的边界优化只有 10~100 ms
（约 1%）——**用 epoch 当尺子，注定测不出来**。

### 5.2 测量分层

| 层级 | 测什么 | 噪声 | 用途 |
|---|---|---|---|
| L0 单算子 | 一次 matmul / conv 的分段耗时 | ±1~5% | 优化决策（用 Bench） |
| L2 epoch | 一个 epoch | ±5~60% | 只用于 ≥10% 的改动，且**同会话跑对照取比值** |

### 5.3 换问法：从「变快了吗」到「到上限了吗」

- pack 25 MB / 1.1 ms → 约 23 GB/s（接近内存带宽 → 继续优化意义不大）；
- matmul H2D 8.5 MB / 0.9 ms → 约 9 GB/s（离 PCIe 上限还有空间 → 值得合并缓冲）。

**换算成有效带宽/有效算力，噪声敏感的问题就变成了几乎无噪声的问题。**

### 5.4 差点误判的一次

A 路径第一次实现时，pack 是 3.1 ms，和旧路径持平→ 差点得出「锁页 + 转换没用」的结论。
真正原因不是锁页，而是**转换是单线程的**（3.1 节）。补上 OpenMP 后 pack 1.08 ms，结论才成立。

**教训：一个优化「没效果」时，先确认它真的执行了（编译选项、路径开关、日志），再怀疑设计。**
