## 二、4×8 分块：一次有收益的失败

### 实测数据

| 阶段 | 4×4 | 4×8 | 变化 |
|---|---|---|---|
| MODE=1 加载 | — | — | **+43%** |
| MODE=2 计算 | 21.87 ms | **35.18 ms** | **+61%** |
| MODE=0 完整 | 25.09 ms | ~39.1 ms | **+56%** |

### 归因（大肥鱼）

```
CTXIT = kColsPerThr × tx × kInnerPerT
  → 同 warp 相邻线程地址步长 = kColsPerThr × kInnerPerT

4×4：步长 188，188 % 32 = 28，gcd(28,32) = 4 → 落 8 个 bank → 2 路冲突
4×8：步长 504，504 % 32 = 24，gcd(24,32) = 8 → 落 4 个 bank → 4 路冲突

每单位计算的 LDS 周期：0.750 → 1.125（+50%）
→ 预测 33.0 ms，实测 35.18 ms（误差 6%）
```

剩余 6% 归因于 `regs` 48 → 80 导致 `blocks/SM` 4 → 3、warp 32 → 24。

**关键旁证**：**MODE=1（加载阶段）也慢了 43%，而该段 `regs = 40`，与寄存器无关**
—— 这排除了「变慢是寄存器溢出造成的」这个假设,实际上大概是因为bank冲突导致的，不过用户之前测试过修改bank冲突的结果，结论是反而更慢

###  副产品：RowOut/ColOut 潜伏 bug 暴露（用户）

```cpp
// 错误写法
int RowOut = (blockIdx.y * kBlockSize + ty) * kColsPerThr;  // 行用了列步长
int ColOut = (blockIdx.x * kBlockSize + tx) * kRowsPerThr;  // 列用了行步长
```

| 分块 | kColsPerThr vs kRowsPerThr | 后果 |
|---|---|---|
| 4×4 | 两者都是 4 → **完全等价** | bug 被掩盖，无害 |
| 4×8 | 4 vs 8 → `RowOut` 被放大 2 倍 | 行号越界守卫提前一倍触发，**行 512~1023 全为 0** |

**512 = 1024/2 正是「行号放大 2 倍」的指纹。**

**结论**：4×8 是负优化，不过在做4*8的过程中，正好顺手将kColsPerThr=kRowsPerThr的要求解耦了，也算有收获吧。

**当前状态**：4×8 已回退（`kColsPerThr = 4`、`Shared_Memory_Size = 24064`），
**但 RowOut 修复保留**（`.cu:85-86` 现为行用 `kRowsPerThr`、列用 `kColsPerThr`）。

## 三、被否掉的两个方案

### 3.1 `PinnedBuffer` 中转方案 —— 否决（用户质疑 / 大肥鱼论证）

**关键问题**：

> 即使创作了固定页缓冲区，还是要拷贝一次

| 路径 | 拷贝趟数 |
|---|---|
| 现状：`cudaMemcpy`（pageable） | 用户内存 → **驱动 staging** → 显存（**2 趟**） |
| `PinnedBuffer` 中转 | 用户内存 → **手动拷到 pinned** → 显存（**2 趟**） |
| 只有源头 pinned | 用户内存 → 显存（**1 趟**）✅ |

**中转方案与现状趟数相同**，还多一次 CPU 参与 → **收益 ≤ 0**。

**根本原因**：pinned 的障碍是**分配器**（`std::vector` 默认分配器给 pageable），
**与元素类型无关** —— `std::vector<float>` 依然 pageable。

若真要 pinned，正解是 `PinnedAllocator`（`cudaMallocHost` / `cudaFreeHost`），
**且必须作用于数据源头**。

实际上，考虑过重构Matrix_Double中的std::vector，但实际上会导致原代码中的大部分std::move()失效，同样得不偿失
### 3.2 `Matrix_Float`（float 矩阵类）—— 否决（大肥鱼论证）

| 理由 | 驳回依据 |
|---|---|
| 算得快很多 | `.cu:47` `extern __shared__ float Mat_Region[]`、`.cu:79` `float sum00...` —— **GPU 计算早已是 FP32**，换存储买不到计算速度。且已实测证伪：float 转换后 GEMM 40 ms → 40 ms 不变（瓶颈是 **LDS 指令条数**，非字节数） |
| 解决 pinned 不兼容 | 障碍是**分配器**，不是元素类型（见上） |
| 方便向量化 | `float4` 只需「元素 float + 对齐 + 连续」，三者已具备（`d_mat1_f` 由 `cudaMalloc` 分配、256 B 对齐；`DoubleToFloat_Kernel` 已合并访存）。要改的是 `.cu:25-28` 的语句 |

**成本**：`Matrix_Double` 有 117 行声明（`Matrix.h:254-371`）+ ~1000 行实现 + 40+ 自由函数 + 27 个 friend；
`Batch_Matrix` / `NeuralNetwork_*` 全部绑定它。新建 float 版要么代码量翻倍，要么写转换函数（比现有边界转换更贵）。

**通用判据**：类型是否携带**需要被保护的不变量**。

| 对象 | 不变量 | 该用什么 |
|---|---|---|
| 设备端 float 中转缓冲 | 只有「生命周期」 | 裸指针 + 容量（现状 ✅） |
| 常驻显存权重 | 生命周期 + 尺寸 | `DeviceBuffer` 句柄（~50 行） |
| 主机侧神经网络矩阵 | 行列 + 运算符语义 | `Matrix_Double`（已有） |

**GPU 内部的 float 数据无行列语义、无运算符、无序列化需求 —— 建类是为不存在的不变量付费。**

## 四、「把整个神经网络搬到显存」—— 可行但暂缓（用户提出 / 大肥鱼评估）

**用户的设想**：参数与运算**完全常驻显存**，CPU 只做控制，加减乘除全在 GPU 上做。

### 两道真门槛

**① 精度门槛 —— 这是入场券，不是优化项**

| 硬件 | FP32 | FP64 |
|---|---|---|
| RTX 5060 Laptop | ~16 TFLOPS | **~0.25 TFLOPS**（消费卡砍到 1/64） |
| i7-14650HX CPU | ~1 TFLOPS | ~0.5 TFLOPS（**反而比 GPU 快**） |

现存网络**全程 double**。**不转 float 就搬过去会更慢** —— 这是可行性问题，不是优化问题。
MNIST 分类用 float32 完全够（PyTorch 默认即 float32）。

**② 粒度门槛 —— kernel launch 开销**

小算子 + 单样本（28×28）场景下，launch 的 μs 级开销会吃掉收益。
既有结论：GPU/CPU GEMM 交叉点约 **N ≈ 40**，必须按 batch 成批调用。
全网络搬到 GPU 后算子调用次数大增，launch 开销占比需重新评估。

### 其他维度

| 维度 | 结论 |
|---|---|
| 算力 | ✅ 绰绰有余 |
| 重构量 | ⚠️ 大 —— 矩阵运算涉及多个文件 |
| 模型规模 | 参数 237 万（double ≈ 18 MB） |

### 与「否决 Matrix_Float」的区别（两者不矛盾）

- `Matrix_Float`：**为加速而新建类** → 无收益 → **否决**
- 全量搬显存：**架构级迁移** → 有收益但成本高 → **暂缓**

**若将来推进**：先转 float（前提），再从**卷积**（占 88% 耗时）单点突破，而非全量重写。

### 6.2 「工作留痕」讨论机制

**每个项目阶段结束、或一天工作结束时，由 AI 主动发起**一次简短复盘。

触发时机：功能跑通 / 一天收尾 / 调试结束 / 用户说了「原来是这样」（**最该记**）

**四个问题**：

1. 这段你真正想通了什么？（不是「做了什么」，而是「从不懂到懂的那一刻」）
2. **哪些是你想的，哪些是 AI 给的？**（认知归因 —— 最有价值）
3. 有哪些招下次还能用？（可迁移的方法论）
4. 这次碰到了什么数学？

**产出落点**：仓库记忆（项目事实）/ 用户记忆（可迁移方法论）/ 项目文档（对外版本）
